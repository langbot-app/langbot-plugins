**Follow-up at `88adecd`:** the five shared agents (Coze/Dify/N8n/Tbox 0.2.2, WeKnora 0.2.3) no longer fall back to a per-run vendor identity — a `sender`-mode run without a trusted Host actor is refused with the plugin's own `<plugin>.identity_unavailable` code before any upstream client is built, and no computed identity contains a run id or a worker revision (WeKnora previously resolved its identity after constructing its client and now validates first, like the other four). `http-certification-tests/test_isolation.py` proves the refusal class and code, that `run()` reports a single `run.failed` carrying it, and that the vendor client class is never constructed; the 36 READMEs of the four `user-id-source` plugins and the five `SHARED_RUNTIME.md` files document the rule. Local evidence: 7/7 isolated plugin suites, 21/21 isolation certification cases, 570 passed with only the 6 known Windows-only vendor-worker failures, ruff clean. `deerflow-agent` and `langflow-agent` still carry an uncalled `_get_user_tag` with the old per-run fallback; it never reaches a vendor and was left untouched.

**Follow-up at `057ace8` (second rejection of FastGPTConnector and RAGFlowConnector):** both at 0.2.2 now make the pre-dispatch fence a precondition and release it only after the result is recorded — a failed Host write of the fence raises `FencePersistError` and aborts before any remote call (previously it was logged and the request was sent anyway, leaving a worker that had fenced the knowledge base in memory with no durable record), `dispatched()` refuses a knowledge base that is already fenced (`FencedKnowledgeBaseError`), and the wrapped operation covers the provider request, the response validation and the durable mapping/tombstone write, so an undecodable body or a cancellation landing after the acknowledgement keeps the knowledge base fenced. RAGFlow's GraphRAG/RAPTOR `except Exception` swallow is gone: a provider-answered non-zero code is a resolved answer while an unresolved outcome propagates and stops the chain, so RAPTOR's success can no longer clear GraphRAG's fence. Certification is `156 passed` with 10 new cases, each shown to fail against the pre-change code. `DifyDatasetsConnector` keeps the previous best-effort persist and release-on-return behaviour: its 0.2.1 passed review and its artifact was deliberately left unchanged, so the stricter lifecycle is not asserted for it in the shared fixture.

**Follow-up at `23e0717` (third rejection of the same two connectors):** FastGPTConnector and RAGFlowConnector at 0.2.3 close three more findings. (1) `is_ambiguous_http_failure` released the protection for every HTTP status; it now releases only for a protocol-confirmed rejection — a 4xx response, or a connection that was never established — and keeps it for 5xx/gateway answers, so a 500 arriving after a possible commit no longer lets later mutations run over an unknown remote state (the FastGPT upload and delete handlers raise `AmbiguousMutationError` for those and report a resolved rejection only for a 4xx). (2) The first fence load was cached per installation without a lock while operations lock per knowledge base, so a snapshot whose read began before a sibling's clear could be installed afterwards and, because the binding was then marked loaded, block an already-resolved knowledge base indefinitely; the read is now single-flight under a per-binding lock and is discarded and re-read (bounded) when the fence generation changed under it. (3) RAGFlow mixed the knowledge-base identity with the collection identity: ingestion keyed config, mappings, locks and fences on `context.get_collection_id()` while creation and deletion used `knowledge_base_id`, so one knowledge base could hold two identities, lose mutual exclusion, and leave deletion unable to find the uploaded record; everything now keys on `context.knowledge_base_id`, `_kb_identity` prefers that attribute over the collection getter, and records already written under the collection key are migrated after a unique legacy match (an ambiguous match refuses and asks for reconciliation). Certification is `177 passed` (21 new cases), each shown to fail against the pre-change code. `DifyDatasetsConnector` and `LangRAG` remain untouched: the shared classifier's 5xx rule is therefore not applied to DifyDatasets, which passed its own review.

**Follow-up at `52465b4` (FastGPTConnector 0.2.4):** the third rejection named the mixed knowledge-base/collection identity for RAGFlow only, but the host contract shows both connectors had it. `LangBot/src/langbot/pkg/rag/knowledge/kbmgr.py` puts `'knowledge_base_id': kb.uuid` and `'collection_id': kb.collection_id or kb.uuid` into the ingestion and retrieval contexts, while `on_knowledge_base_create` and `call_rag_delete_document` always pass `kb.uuid`; the SDK's `get_collection_id()` returns `collection_id or knowledge_base_id`, so a knowledge base bound to an existing vector collection gave ingestion a different key from creation and deletion — two locks, two fences and a document mapping that deletion could not find. FastGPT now keys the stored config, the upload-intent check, the pending intent, the created mapping, the deletion tombstone and the dispatch identity on `context.knowledge_base_id`, and `_kb_identity` prefers an argument's `knowledge_base_id` over its collection getter; records an earlier revision wrote under the collection key are migrated after a unique legacy match (an ambiguous match refuses). Its retrieval path needs no change: it is not serialized and reads only context creation settings. Certification is `180 passed` (three new cases, each failing before the change), and the two bundles' shared functions are now identical modulo docstrings — `is_ambiguous_http_failure`, `_load_fences`, `_read_fences`, `_bump_fence_generation`, `dispatched`, `fence`, `clear_fence`, `_kb_identity`, `_legacy_document`, `_migrate_legacy`, `_load_document`, `_save_document`.

**Follow-up at `504cc46` (fourth rejection of the same two connectors):** the scan-based legacy migration the two previous rounds added was itself unsafe and is now removed from both bundles (FastGPTConnector 0.2.5, RAGFlowConnector 0.2.4). With a mapping recorded for knowledge base A and none for B, a delete under B adopted A's current record, copied A's configuration under B's key and — when the upstream target and dataset matched — deleted A's upstream document. `ConfigStore._legacy_document`, `ConfigStore._migrate_legacy` and the `_load_document` branch that called them are deleted; `_load_document` resolves only the exact mapping of the requested knowledge base (its canonical record, or a record that same knowledge base itself wrote and that carries the older Host revision's file UUID, still refusing an ambiguous match) and refuses when there is none, with no provider request and no storage write, so an ingest also no longer mistakes another knowledge base's pending record for its own intent. Historic collection-keyed data now moves to the canonical key only through explicit reconciliation. Certification replaces the two migration cases per plugin with a cross-knowledge-base deletion case (which fails against the pre-change code: `delete_document('B', 'shared-doc')` returned True and dispatched A's delete) and a no-false-intent case; the suite stays at 180 passed. The two notes above describe the migration this commit withdraws — they record history, not current behaviour.
